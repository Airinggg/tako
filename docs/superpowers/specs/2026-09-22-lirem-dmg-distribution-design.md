# Distributing tako to Lirem as a macOS `.dmg` — Design Spec

Status: Draft, awaiting review
Author: brainstormed with the product owner, 2026-09-22
Related: `bin/omnibrain` (`doctor`/`setup` commands), `lib/cli/doctor.ts`,
`lib/cli/setup.ts`, `lib/cli/serve-runtime.ts`, `scripts/demo.ts`,
`docs/CONNECTOR_CREDENTIALS.md`

## 0. Objective

Package tako as a `.dmg` so it can be handed to Lirem's pilot Mac as a
tangible installable artifact, instead of the owner manually cloning the
repo and running dev commands on the customer's machine. Confirmed
constraints from brainstorming: the target machine is a Mac (native Ollama
performance, no Docker GPU-passthrough loss); the owner personally
performs the initial install and all future updates (not Lirem's staff);
and once running, tako should be an always-on background service Lirem's
staff never has to start, stop, or think about.

## 1. Non-goals

- **Not a signed, notarized `.app` bundle.** The installer is a source
  tree plus a shell script, not a native macOS application. A polished
  `.app` (code signing, notarization, Sparkle-style auto-update) is real
  engineering investment that only pays off with many customers/machines
  to support — this is a single pilot machine the owner maintains
  directly.
- **Not self-updating.** The owner updates the pilot machine themselves
  (remote access or on-site), the same way this session already proved
  out for a real fix (cherry-pick a commit, restart the process). No
  "check for updates" UI, no background updater.
- **Not a no-terminal experience.** The owner is technical and is doing
  the install themselves — `Install.command` opens Terminal when
  double-clicked (standard macOS behavior for `.command` files) and that
  is an acceptable and expected part of setup, not something to hide.
- **Not automated connector credential provisioning.** Each customer's
  Slack/Drive/Discord tokens are unique and cannot be generated by an
  installer — the owner still fills in `config/connectors.json` by hand,
  the same way they already do today, guided by the existing
  `docs/CONNECTOR_CREDENTIALS.md` guides.
- **Not a rebuild of `doctor`/`setup`.** The installer script orchestrates
  and calls the existing `bin/omnibrain doctor` and `bin/omnibrain setup`
  commands rather than reimplementing their checks.

## 2. Architecture overview

The `.dmg` contains two things when mounted:

1. **The tako source tree** (`.git`, `node_modules`, and any local
   `config/*.json`/`.env` excluded from the packaged copy — those are
   either regenerated on the target machine or filled in by the owner
   there, never shipped with real or stale credentials baked in).
2. **`Install.command`** at the top level — a shell script, executable
   bit set, so double-clicking it in Finder opens Terminal and runs it
   (standard `.command` file behavior, no separate app wrapper needed).

No compiled binary, no `bun build --compile` step: `packages/brain`'s own
`CONTRIBUTING.md`/`CHANGELOG.md` document that compiling to a native
binary needed several dedicated workarounds for WASM/PGLite asset
embedding (`pglite-embedded-assets.ts`, `admin-embedded.ts`,
`schema-pack/bundled-assets.ts` all exist specifically for this). Running
from source via `bun scripts/demo.ts`, as the dev environment already
does, avoids that entire class of risk. Neither `package.json` (tako's
own) nor the vendored `packages/brain/package.json` declares a native
(compiled) dependency, so there is no cross-machine binary-compatibility
concern to offset against that choice — `npm install` on the target
machine is sufficient and safe.

`Install.command` is idempotent and runs in two passes, split by the one
step that genuinely cannot be automated (credential entry):

**Pass 1 — machine provisioning** (`./Install.command`, first run):
1. Install Homebrew if `brew` is not found.
2. Install `bun` and `ollama` via Homebrew if not already present (each
   check is independent — an already-satisfied prerequisite is skipped,
   not reinstalled).
3. `ollama pull bge-m3` and `ollama pull qwen2.5:3b-instruct` (the same
   model list `bin/omnibrain doctor`/`README.md` already document —
   sourced from one place, not duplicated as a second hardcoded list; see
   Task-level detail in the implementation plan for exactly where).
4. Copy the app source tree to `~/tako` (not `/Applications` — this is a
   plain source tree, not a signed bundle, and `~/tako` avoids any
   permission friction `/Applications` can introduce for a non-bundle
   copy).
5. `cd ~/tako && npm install`.
6. Run `bin/omnibrain setup` (already scaffolds `config/*.json` from the
   committed `*.example.json` templates and reports which env vars/
   credentials are still missing).
7. Print explicit next-step instructions: fill in `config/connectors.json`
   with Lirem's real per-connector credentials (pointing at
   `docs/CONNECTOR_CREDENTIALS.md`), then re-run `Install.command`.
8. Exit 0. Does **not** start the server yet — there is nothing useful to
   serve without at least one configured source.

**Pass 2 — go live** (`./Install.command`, re-run after credentials are
filled in): detects that `config/connectors.json` already has real values
(not just the scaffolded placeholders) and, instead of repeating pass 1's
steps, moves straight to:
1. Run `bin/omnibrain doctor` and print its report. If any check fails,
   stop here with that report — do not install the LaunchAgent against a
   machine that isn't ready.
2. Install and load a `launchd` LaunchAgent (`~/Library/LaunchAgents/
   com.tako.demo.plist`) that runs `bun scripts/demo.ts` from `~/tako`
   at login, with `KeepAlive: true` (auto-restarts on crash) and stdout/
   stderr redirected to `~/Library/Logs/tako/demo.log` — a real,
   reboot-durable location, not `/tmp` (which can be cleared).
3. `launchctl load` the plist so the server starts immediately, without
   requiring the owner to log out and back in.
4. Open `http://localhost:4400` in the default browser once the server
   responds (poll, bounded wait — same pattern already used and
   fixed-for-real-readiness in `scripts/demo.ts`'s Agent Provisioning
   route this session, not a fixed sleep).

Re-running `Install.command` a third time (e.g. after a future update) is
safe: prerequisite checks in pass 1 are already-satisfied no-ops, and pass
2 detects the LaunchAgent already exists and reloads it (`launchctl
unload` then `load`) instead of erroring on a duplicate install.

## 3. Update workflow

No mechanism is built for this beyond what already exists. To ship a fix
to the pilot machine, the owner (remote access or on-site):

```
cd ~/tako
git pull                      # or: git cherry-pick <sha> for a scoped fix
npm install                   # only if dependencies changed
launchctl unload ~/Library/LaunchAgents/com.tako.demo.plist
launchctl load ~/Library/LaunchAgents/com.tako.demo.plist
```

This is the exact sequence already exercised successfully in this session
(cherry-picking the Gemini-retry fix onto a running demo server) — the
only change from what was already done manually is `launchctl`
unload/load in place of `kill` + a manually backgrounded `bun` process,
so the server survives a reboot between visits instead of needing to be
started by hand again.

## 4. GBRAIN_HOME and configuration

Lirem's machine keeps the code's built-in default (`~/.aletheia-brain`),
not the owner's own dev override (`~/.tako-brain` via `.env`) — confirmed
in brainstorming: the two are functionally identical, and there is no
reason to add an unnecessary `.env` override just for naming symmetry
across machines the owner does not need to treat interchangeably.

## 5. Error handling

- Every provisioning step in pass 1 checks its own precondition
  (`command -v bun`, `command -v ollama`, does `~/tako` already exist,
  does `config/connectors.json` already have a real value vs. the
  scaffolded placeholder) before acting, so re-running the script never
  clobbers already-completed work or already-entered credentials.
- A failed step (no internet, a Homebrew install failing, an `ollama
  pull` timing out) stops the script immediately with a message naming
  the failed step and its actual error output — never silently continues
  into a half-provisioned state.
- Pass 2 treats a failing `omnibrain doctor` report as a hard stop before
  the LaunchAgent is ever installed — the server should never go live
  against a machine `doctor` itself says isn't ready.
- Installing the LaunchAgent is itself checked for an existing plist
  first (load-if-absent, unload-then-reload if already present) rather
  than erroring on `launchctl load` of an already-loaded label.

## 6. Testing strategy

This is a real-machine installer, not something CI can run end to end —
verification is a dry run on the owner's own Mac (or a scratch user
account) before it ever touches Lirem's pilot machine, the same way any
installer gets tested before a real deployment.

What can and should be unit-tested without invoking Homebrew/Ollama for
real:
- The "already installed, skip" vs. "not installed, provision" decision
  logic, as a pure function given a fake `command -v` result — mirrors
  how `lib/cli/doctor.ts`'s checks are already pure functions taking
  parsed input rather than shelling out inside the test.
- The generated LaunchAgent plist is valid XML with the expected keys
  (`Label`, `ProgramArguments`, `KeepAlive`, `StandardOutPath`,
  `StandardErrorPath`, `WorkingDirectory`) — a template-rendering pure
  function, tested against a fixed set of inputs.
- Pass-1-vs-pass-2 detection (does `config/connectors.json` still look
  like the scaffolded placeholder, or does it have real values) reuses
  `lib/cli/setup.ts`'s existing `missingEnvVars`/`extractEnvPlaceholders`
  logic rather than a new, separately-tested heuristic.

## 7. Removal / fallback

To decommission the pilot install: `launchctl unload` and remove the
plist, `rm -rf ~/tako`, `brew uninstall ollama bun` if nothing else on the
machine needs them. No tako-owned system-level state exists outside
`~/tako` and the one LaunchAgent file, so removal is a short, complete
list — nothing else on the machine to clean up.
