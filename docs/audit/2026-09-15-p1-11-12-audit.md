# P1-11 and P1-12 audit — 2026-09-15

Read-only audit against `docs/PROTOTYPE_SECURITY_CHECKLIST.md`'s P1-11
(retention/deletion) and P1-12 (backup/restore). No Lirem-specific
contractual retention or backup numbers exist anywhere in the repo — any
number used below is a proposed default, not a committed requirement.

## P1-11 — Retention/deletion: PARTIAL

More real machinery exists than the checklist's placeholder status
suggested:

- `packages/brain/src/core/destructive-guard.ts`'s `softDeleteSource()`
  sets `archived=true` + a 72h `archive_expires_at`, hides the source from
  search immediately (`buildVisibilityClause`). After the TTL, the
  autopilot purge phase (`cycle.ts:1660`) permanently deletes the rows,
  cascading to `content_chunks`/embeddings/links via `ON DELETE CASCADE`.
- `gbrain delete <slug>` (soft) and `gbrain pages purge-deleted`
  (admin+local-only hard-delete) already exist as CLI commands.
- Every connector already calls `pruneStale()`
  (`lib/connectors/shared/prune.ts`) to remove `.md` files that no longer
  exist upstream — confirmed live via `brain-sources/`'s real git history.
- `sync-delta.ts` diffs git commits and feeds deletions into the sync
  manifest — removing a file and re-syncing does propagate into the index,
  it does not silently retain stale content.

What's missing:

- The 72h TTL (`SOFT_DELETE_TTL_HOURS`, `destructive-guard.ts:75`) is a
  hardcoded global constant — no per-instance configurable retention
  period exists anywhere in `config/*.json`.
- **Zero app-level (tako) entry point.** `scripts/demo.ts` has no
  delete/purge route at all — the real deletion capability lives entirely
  in the underlying `gbrain` CLI, never exposed through the product
  surface Lirem would actually use.
- No cache-clearing tied to deletion, because no deletion trigger exists
  at the app layer to begin with.
- No create→delete verification has ever been run and recorded.

## P1-12 — Backup/restore: FAIL

- `gbrain backup` is **not a backup** — its own file header says it's a
  "monthly backup-coverage check: if this disk died, could I recreate my
  agent?". It only checks whether source git repos have a configured
  `origin`; it never creates, encrypts, or stores anything.
- For tako's actual setup (PGLite + `brain-sources/` with no remote), the
  coverage checker's own logic flags the worst case: pages live only in
  the local DB, a disk loss loses all of them (`coverage.ts:414-430`).
- Confirmed live: `git -C brain-sources remote -v` is empty — real commit
  history, no push-based backup in practice.
- No backup of `~/.aletheia-brain` anywhere, no encryption at rest for
  either store (`docs/COMPANY_SECURITY_BASELINE.md` lists this only as an
  aspirational enterprise-tier principle, not something built).
- `docs/ROLLBACK_RUNBOOK.md` is confirmed code-release-only — its own
  "what this doesn't cover" section never mentions data restore.
- No restore has ever been documented or tested; no RTO/RPO exists
  anywhere except as the checklist's own requirement line.

No contractual anchor exists for either item's numbers — see the open
questions in the ledger/conversation for the defaults chosen.
