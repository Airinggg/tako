## P0-01 — 公開範囲 (exposure scope): FAIL — by design, not by accident

**Evidence:**
- `scripts/demo.ts:1000-1002` — `Bun.serve({ hostname: "127.0.0.1", port: PORT, idleTimeout: 240, ... })`. Bound to loopback only, not `0.0.0.0`.
- `scripts/console.ts:239-240` — same: `hostname: "127.0.0.1"`.
- Full route list, `scripts/demo.ts` (grep `pathname ===`, lines 1007-1093): `/`, `/api/overview`, `/api/ask` (POST), `/api/page`, `/api/access`, `/api/skills`, `/api/automations/create` (POST), `/api/tasks`, `/api/reviews`, `/api/activity`, `/api/activity/retry` (POST), `/api/redact-try` (POST), `/api/review-submit` (POST), `/api/review-decide` (POST), `/api/connectors`, `/api/mcp-industrial`, `/api/connectors/save` (POST), `/api/connectors/test` (POST), `/api/connectors/sync` (POST).
- `scripts/console.ts:244-266`: `/`, `/api/brains` (GET), `/api/members` (GET), `/api/invite` (POST), `/api/revoke` (POST).
- No auth check anywhere in either file — no `Authorization`, cookie, session, or token gate on any route (grep for `Authorization|session|cookie` in demo.ts only matched the connector-credential-testing code at lines 643-646, which is outbound, not inbound auth).
- `/api/connectors/save`, `/api/connectors/sync`, `/api/activity/retry`, and console's `/api/invite`/`/api/revoke` (which mints and revokes live gbrain client credentials) are all reachable by anyone who can reach the port, no different from the public ask screen.

**Rationale:** No authentication layer exists at all — every "admin" route sits on the exact same unauthenticated surface as the public Ask screen. The only real control is that both servers bind to `127.0.0.1`. Minimal fix: shared-secret/basic-auth middleware in front of the mutating routes before this is ever deployed anywhere off `127.0.0.1`.

## P0-04 — 入力制限 (input validation): FAIL

- Every body-parsing call (`/api/ask`, `/api/automations/create`, `/api/activity/retry`, `/api/redact-try`, `/api/review-submit`, `/api/review-decide`, `/api/connectors/save`, `/api/connectors/test`, `/api/connectors/sync`) is a bare `await req.json()` with no size cap or schema validation.
- No `maxRequestBodySize` configured anywhere.
- Malformed JSON falls through to the single outer catch (`scripts/demo.ts:1099-1100`) and returns HTTP 500 with the raw parse-error message, not a clean 400.
- `console.ts`'s `invite()` (lines 217-228) is the one exception with real regex validation.

Minimal fix: size-limited body reader + per-endpoint schema validation (e.g. zod) + 400-vs-500 mapping for parse failures.

## P0-05 — XSS: PASS, with one gap

- `escHtml()` (`scripts/demo.ts:806`) and client-side `esc()` (`scripts/demo.ts:1995`, mirrored in `console.ts:285`) both exist and are applied consistently.
- LLM answer output (`scripts/demo.ts:2076`) passes through `esc(cleanAnswer(...))` before `innerHTML` — `cleanAnswer()` doesn't strip HTML but `esc()` neutralizes it.
- Connector document body uses `textContent`, not `innerHTML` (`scripts/demo.ts:2051`) — cannot execute injected markup regardless of content.
- No `dangerouslySetInnerHTML` or Markdown-rendering library anywhere in the repo.
- **Gap:** no `Content-Security-Policy` header anywhere; no dedicated automated XSS regression test for the current demo/console servers (the existing `tests/rendered-html.test.mjs` targets the older, separate prototype).

Minimal fix: add a CSP header (even `default-src 'self'`) and a regression test posting a `<script>`-laden fixture through `/api/ask`.

## P0-06 — エラー表示 (error display): FAIL

- Top-level handler (`scripts/demo.ts:1099-1101`): `catch (err) { return json({ error: (err as Error).message }, 500); }` — returns `err.message` verbatim on every uncaught exception, for every route.
- Concrete leak path: `lib/eval/qa.ts:41-42` (`gb()`) throws `` `gbrain ${args[0]}: ${why}` `` from the child process's raw stderr, which can include internal file paths / `GBRAIN_HOME` paths / stack fragments. This flows straight to the client via `/api/ask`, `/api/page`, `/api/access`, `/api/skills`, `/api/tasks`, `/api/reviews`, `/api/activity`, `/api/connectors`.
- `scripts/console.ts:267-268` has the identical pattern.

Minimal fix: catch known-internal errors, log full detail server-side only, return a generic message + correlation id to the client.

## P0-07 — 乱用防止 (abuse prevention): FAIL — confirmed still open

- No rate-limit/throttle/debounce/maxRequestBodySize logic anywhere in `scripts/`/`lib/` (the one `rate-limit` hit is Discord's own outbound limit being respected, not an inbound guard).
- `/api/ask` → `answerFromSource()` has a 10-minute per-call timeout (`lib/eval/qa.ts:65`) but no concurrency/rate cap.
- `/api/activity/retry`: the `READ_ONLY` guard added in the tako redesign's final-review fix round (`scripts/demo.ts:301`) blocks it entirely when `DEMO_READONLY=1`, but when unset (the default), there is still no rate limit or debounce.
- `/api/connectors/sync` has the same gap.
- `idleTimeout: 240` is a per-connection idle timeout, not a rate/payload control.

Minimal fix: per-IP/global concurrency + rate limiting in front of `/api/ask`, `/api/activity/retry`, `/api/connectors/sync` at minimum.

- No deployment config (`Dockerfile`, `docker-compose.yml`, `vercel.json`, `wrangler.toml`, `fly.toml`) found anywhere for the current `tako`/brain servers.

**Design requirement before any public HTTPS deployment:** TLS termination, HSTS, CSP, `X-Content-Type-Options: nosniff`, and — once any session/cookie auth exists — `Secure; HttpOnly; SameSite=Strict` flags.
